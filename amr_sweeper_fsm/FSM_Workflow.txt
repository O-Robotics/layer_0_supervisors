AMR Sweeper FSM (Layer 0) — FSM Workflow
===========================================

Scope
-----
This document describes the workflow of the AMR-Sweeper's FSM in fsm_layer_0 (amr_sweeper_fsm):
  - what the supervisor does
  - what each state is responsible for
  - how startup gating works (INITIALIZING → IDLING / FAULT)
  - how `state_parameters.yaml` and per-state profile files tune behavior without code changes


Architecture at a glance
------------------------
Nodes (default namespace: /amr_sweeper):
  - supervisor                     (rclcpp::Node)
  - initializing_state             (LifecycleNode)
  - idling_state                   (LifecycleNode)
  - running_state                  (LifecycleNode)
  - charging_state                 (LifecycleNode)
  - fault_state                    (LifecycleNode)

Only ONE lifecycle state node is to be ACTIVE at a time.
All other lifecycle state nodes are typically INACTIVE (or UNCONFIGURED) but alive (running).

FSM-state name set:
  INITIALIZING, IDLING, RUNNING, CHARGING, FAULT

Profile ID bands (100-wide band of profiles per FSM-state)
---------------------------------------------
  INITIALIZING : 000 - 099   (bridge 000, default 001, alternate 002, debug 003)
  IDLING       : 100 - 199   (bridge 100, default 101, testing 110)
  RUNNING      : 200 - 299   (bridge 200, default 201, mapping 202, routed 203, teleop 204)
  CHARGING     : 300 - 399   (bridge 300, default 301)
  FAULT        : 400 - 499   (default 400, empty 401)


FSM workflow
------------
Launch:
  - Start supervisor + all 5 state lifecycle nodes.

Discovery:
  - Supervisor discovers available nodes/services and monitors readiness.

Request and arbitration:
  - External clients call /amr_sweeper/request_state (RequestState.srv).
  - Supervisor arbitrates requests by priority/force and sets:
      desired_state
      desired_profile_id

Transition:
  - Supervisor manages lifecycle transitions so that only one FSM-state is ACTIVE.
  - If desired_state changes, the supervisor deactivates the current state and activates the target state.
  - If desired_state is the same but desired_profile_id changes, the supervisor re-enters the same state
    (deactivate → cleanup/configure → activate) so the new profile is applied cleanly.
  - Requests are accepted only when the target profile both matches the state's numeric band and exists in that state's profile YAML.


State behaviour (design intent)
------------------------------

INITIALIZING
  - Perform a full startup systems check.
  - The default startup profile validates layer 1 hardware, layer 2 controllers, layer 3 localization/navigation/mapping,
    plus mission-parser and scheduler readiness.
  - Profile 001 is the normal startup validation path.
  - Profiles 000, 100, 200, and 300 are empty bridge profiles chained as 000 -> 100 -> 200 -> 300 -> 400.
  - Profile 003 starts the same layer bringup commands as 001 but keeps them non-blocking and does not auto-transition to IDLING or FAULT.
  - Readiness failures or process failures escalate according to per-process error policy, typically into FAULT profile 400.

IDLING
  - Robot is safe and ready.
  - Default profile 101 launches reduced layer 1 hardware bringup, `amr_sweeper_vda5050_parser`, and `amr_sweeper_scheduler`.
  - `amr_sweeper_vda5050_parser` watches the missions directory and keeps parsed mission artifacts updated.
  - `amr_sweeper_scheduler` watches the schedule and asks the supervisor to enter RUNNING when a valid
    WORK window becomes active.
  - `amr_sweeper_mission_executor` is not launched by the FSM profile itself, but it remains the component that owns
    mission preparation, execution-folder creation, and RUNNING-profile routing for scheduler/manual flows.

RUNNING
  - RUNNING is profile-driven rather than a single mode.
  - Profile 201 is the default mission execution stack.
  - Profile 202 is manual mapping.
  - Profile 203 is manual routed missions.
  - Profile 204 is manual teleoperation.
  - Profiles that use mission execution directories pass them into layer 3 bringup through the
    `runtime.mission_execution_directory` parameter placeholder.

CHARGING
  - Charge supervision with layer 1 hardware bringup in profile 301.
  - No automatic charge-complete transition is currently defined in the shipped charging profiles.

FAULT
  - Terminal fault profile intended for containment.
  - Profile 400 is empty and does not auto-transition further; profile 401 is also empty.
  - No automatic transition out of FAULT is configured in shipped profiles.


How configuration tunes behaviour
--------------------------------
The FSM is configured by two YAML layers:

1) config/state_parameters.yaml
   - Per FSM-state fault block 
   - Path to that state's profile file.

2) config/profiles/<state>_profiles.yaml
   - Contains the processes and rules for each profile in that FSM-state.
   - Processes may define internal recovery/degraded actions and may escalate to a state fault.


Operational notes
-----------------
- Add or change a subsystem:
  1) Add/modify the process definition inside the relevant per-state profile YAML file.
  2) Add per-process rosout triggers for RECOVER/DEGRADED/FAULT behavior as needed.
  3) Use the state-level fault block in state_parameters.yaml for global safety triggers.
